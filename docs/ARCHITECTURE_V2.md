# Архитектура mytgbot v2

## Цель

Развивать бота без остановки действующей версии. Новые функции добавляются
отдельными сервисами и подключаются к существующим обработчикам только после
автоматической проверки.

## Правила

1. `bot.py` отвечает за сборку и запуск приложения, а не за бизнес-логику.
2. Обработчики Telegram принимают данные и вызывают сервисы.
3. Сервисы реализуют сценарии: акты, АВР, ведомости, заказы и согласование.
4. Работа с БД сосредоточена в моделях и репозиториях.
5. Шаблоны документов хранятся в `templates/`, готовые документы — вне Git.
6. AI формирует структурированные данные, но итоговый документ создаёт
   детерминированный генератор.
7. Все Telegram-обработчики подключаются только через `handlers/registry.py`;
   порядок регистрации считается частью публичной архитектуры приложения.

## Текущее подключение модулей

`bot.py` создаёт экземпляр Telegram-бота и вызывает единый реестр. Реестр
подключает сообщения, документы, категории, ремонтные ведомости и диалог акта.
Устаревший `handlers/callback_handlers.py` сохранён только как совместимый
модуль и больше не участвует в запуске.

Навигация по судам, разделам и пунктам имеет одну реализацию:
`document_manager.py` + `handlers/repair_handlers.py`. Модуль `navigation.py` отвечает
только за категории и версии документов и больше не содержит дублирующих
запросов к ремонтной ведомости.

Активные Telegram-модули находятся в пакете `handlers/`:

- `document_handlers.py` — загрузка, замена и удаление документов;
- `category_handlers.py` — категории, версии, скачивание и согласование;
- `repair_handlers.py` — загрузка ведомостей и навигация по ним.

Одноимённые корневые файлы оставлены как короткие совместимые импорты. Новая
логика в них не добавляется.

Наличие импортированного AI-модуля не означает готовность внешнего сервиса.
Интерфейс показывает YandexGPT активным только при наличии API-ключа и folder
ID; генератор XLSX и остальные локальные функции работают без внешнего AI.

## Первый этап

- утверждённый шаблон `templates/defect_act_template.xlsx`;
- генератор `services/defect_act_service.py`;
- проверка заполнения и очистки плейсхолдеров;
- затем подключение генератора к диалогу создания акта.

## Профили дефектации

Основной шаблон остаётся единым. Профиль меняет уточняющие вопросы и правила
формирования строк: трубопроводы, теплообменники, гидравлика,
электрооборудование, палубные механизмы/редукторы, вентиляция и общий режим.

## Реквизиты акта

Судно, пункт РВ, описание и количество загружаются из ремонтной ведомости.
ФИО ответственного берётся из профиля пользователя. Номер заказа запрашивается,
поскольку в текущей модели ремонтной ведомости отдельного поля для него нет.
Перед созданием файла бот показывает сводку реквизитов для подтверждения.

## Целевая структура

```text
app/
  handlers/       Telegram-сценарии
  keyboards/      клавиатуры
  states/         состояния диалогов
  services/       бизнес-логика
  repositories/   запросы к БД
  models/         модели данных
  ai/             извлечение структурированных данных
  utils/          общие небольшие функции
templates/        утверждённые шаблоны
runtime/          временные и сформированные файлы, вне Git
tests/            автоматические проверки
docs/             документация
```

Полный перенос в `app/` выполняется по модулям после покрытия тестами, без
одновременного переписывания работающего бота.
